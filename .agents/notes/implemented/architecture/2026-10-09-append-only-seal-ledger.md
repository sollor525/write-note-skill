# Agent Note: 归档封印用只增不改的封印史，而不是单个哈希清单

Status: implemented

## Problem

归档笔记的冻结契约原本只靠 `archived/manifest.json` 里一张 `路径 → sha256` 的映射表。哈希值本身写在同一个可写文件里，没有任何外部锚点，于是"防止篡改"退化成"和自我保持一致"：

删掉 `manifest.json`，再按文档推荐的补封印命令跑一次 `verify-archived-agent-notes.ts --write`，被改过的归档正文就会**静默获得一个新封印**，此后一切正常。README 里"谁动了归档里的一个字，校验当场报警"这句承诺因此不成立。

更糟的是，这条绕过路径是**我们自己写进文档推荐流程的**（"历史包袱补齐"一节），使用它的人不会觉得在做危险操作。

## Decision

封印拆成两个文件，两者必须逐项一致：

- `archived/manifest.json` 是 `路径 → sha256` 的派生索引，只能由命令与账本一起更新；
- `archived/.seal-ledger.json` 是按路径排序的账本，每条记录带链接前一条的链式哈希 `sha256(prevChain + "\n" + key + "\n" + seal)`。新增路径可以重算后续链值；受保护的是已有路径与摘要。

校验同时检查账本链、索引条目集合、磁盘文件及内容摘要。删除末条不会破坏前面的链，因此不能用链校验代替集合对比，也不能在校验期间修补读入的索引。

- `--write` 只新增，不能重封已有内容或重建单独丢失的元数据；
- `--reseal` 要求原账本有效，可显式采纳正文变化或从完整账本恢复缺失索引，不能修复损坏的链；
- 缺失的账本必须恢复。首次迁移时，两份元数据均不存在才允许建立初始封印；
- 有效 Git 基线中的已有路径与摘要必须保留。基线已有账本时，新增归档必须对应基线里存在的 `implemented/` 笔记，来源路径按 `AGENT_NOTE_ROOT` 解析；
- 显式 `AGENT_NOTE_ARCHIVE_BASE_REF` 无法解析或读取时失败。未配置且缺少 Git 或 HEAD 尚无提交时才警告降级，只验证本地一致性。

两个文件由 `scripts/seal-store.ts` 共用实现，并成对更新。归档的准备、失败恢复与解析器约束见[校验与归档一致性](../bug-fix/2026-10-10-validation-and-archive-consistency.md)。

## Alternatives considered

- **给封印加 HMAC 或签名**——这是唯一能真正防篡改的做法，但密钥要么进仓库（等于没有），要么进 CI secret（本地就退化），并且把"零配置、`npx tsx` 直接跑"这个核心卖点换掉了。留下的是更差的中间态：看起来有密码学保护，实际取决于密钥管理，而本项目没有任何密钥管理。放弃。
- **只保留单个 manifest，但让 `--write` 拒绝任何已存在条目**——能挡住重封，却挡不住"删掉整个文件再重建"，因为删除后没有任何东西能证明曾经封印过什么。实测确认这条路径可绕过，因此单独一个文件不足以承载冻结契约。
- **把 manifest 提交进 git 就够了，不做封印史**——git 确实提供外部见证，但只有在 CI 把基线指向变更前的 commit 时才成立；本地 `HEAD` 是空操作（对比的是自己）。而且"未提交就被改"这个窗口里毫无保护。git 与封印史解决的是不同问题，两者都要。
- **什么都不做，只在文档里警告**——本项目的前提就是"写在散文里的规矩等于没有规矩"，用警告替代机制与自身立场矛盾。

## Consequences

- **收益**：单独删除索引条目、截断账本尾部、删除文件以及快照内容变化都会失败；有效 Git 基线还可以发现一起改写本地封印的行为。
- **代价与上限**：索引与账本仍在同一可写仓库内，本地一致性不能证明历史未被共同改写。CI 必须使用变更前的可信提交；`--reseal` 生成的新封印仍受随后基线校验约束。

## Verification

- `npm run test-gates` 覆盖首次封印、失去索引或账本、末条删除、文件删除、损坏链、显式重封、无效 Git 引用、自定义笔记根目录以及独立的历史篡改夹具。
- 链完整性由 `verifyChain()` 检查，索引与账本一致性由 `sealIndexErrors()` 检查，归档 CLI 与校验器共用这些函数。
