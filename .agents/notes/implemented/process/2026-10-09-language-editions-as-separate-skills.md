# Agent Note: 语言做成两个可独立安装的 Skill，而不是一份双语 Skill

Status: implemented

## Problem

需要同时支持中文与英文使用者，并且让安装时能选语言。

最初的想法是"一个 Skill、两种语言"，但安装器的实际行为堵死了这条路，而且这两点都不在文档里：

1. **复制不保留符号链接。** 安装器用 `cp` 分发，会跟随链接把内容复制过去，并在遇到损坏链接时跳过。所以"共享一份脚本、各语言只放文档"的布局在安装后并不成立。
2. **没有语言或标签维度。** 安装器的发现逻辑只遍历目录（`skills/`、`.agents/skills/` 等容器），按名字列出 Skill；不存在"同一 Skill 的语言变体"这个概念，也没有任何按 locale 过滤的开关。

因此语言选择必须落在**可独立发现的 Skill** 这一层，而不是某个 Skill 的属性。

## Decision

仓库提供两个并列的可安装 Skill，语言选择就是选 Skill：

- `skills/write-notes/`——中文版，`SKILL.md` 的 `name: write-notes`；
- `skills/write-notes-en/`——英文版，`name: write-notes-en`。

两者的 `SKILL.md`、`references/`、`templates/` 各自成文；**门禁脚本与看板模板按原样各存一份**（语言中立的代码不翻译）。安装时用 `--skill` 二选一，省略则由安装器询问。

目录名必须与 frontmatter 的 `name` 一致，否则安装会撞名。

唯一有意不同的是 `build-board.ts`：它打印面向用户的控制台信息，英文版必须是英文，因此它是共享清单的例外。其余脚本由测试逐字节断言两版相同，防止漂移。

## Alternatives considered

- **一份 Skill，正文双语并列**——对 `SKILL.md` 而言会让指令长度翻倍，而模型只需要一种语言；更关键的是它并不能让用户"选择语言"，只是把两份内容都塞给模型，与需求不符。放弃。
- **`skills/write-notes/` 只放语言文件，脚本用符号链接共享**——本地看着优雅，安装后立刻失效：复制会跟随链接，于是每个语言版本仍各自持有一份真实脚本，"共享"只是幻觉，还多了一层损坏链接的风险（安装器会跳过损坏链接并只打印警告）。放弃。
- **只做英文，中文用户自己看英文**——仓库现有内容全是中文，且中文是这个方法的原作者语言；反过来删掉中文会丢弃已经写好的主体内容。两个语言各自成文更诚实。
- **让脚本读取一个语言配置来切换输出**——为此要在无依赖的 `tsx` 脚本里引入配置解析与两套文案，收益只是"少一个文件"，而代价是每个脚本都要处理语言分支。放弃，改为只让唯一有用户可见输出的脚本分叉。

## Consequences

- **收益**：用户在安装那一刻明确选择语言；两版结构完全对称，便于对照与维护；共享脚本的漂移由测试守住，而不是靠人记得同步。
- **代价与已知上限**：共享的 `scripts/` 与看板模板在仓库里各存一份，仓库变大了一倍（每版 23 个文件）。脚本内的注释保持中文（除 `build-board.ts` 的输出），因为它们是同一份实现——这是刻意的取舍，代价由维护者承担，不影响使用者。**看板界面文案目前只有中文**：模板内含约 1300 个汉字的内嵌演示数据，界面文案硬编码在同一个文件里、没有 i18n 层，为一个次要辅助工具重写渲染层不划算；两版共用同一个模板，需要英文界面时改这一个文件即可。该限制已写进 README 与两版 `SKILL.md`。

## Verification

- `npm run test-gates` 断言：两版 `SKILL.md` 都存在、frontmatter 的 `name` 与目录同名、英文版没有漏译中文（门禁确实接受的中文小节别名列入允许清单）、共享文件在两版间逐字节相同、两版 `SKILL.md` 的相对链接都能解析、英文版自己的门禁能跑通英文笔记。
- `npm run test-skill-install` 断言 `--skill write-notes` 不会装上英文版、`--skill write-notes-en` 不会装上中文版，且交付的文件树与源目录逐字节一致。
