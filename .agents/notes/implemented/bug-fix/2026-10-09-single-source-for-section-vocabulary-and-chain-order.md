# Agent Note: 门禁与归档器共用同一套词汇表，且封印链按排序顺序定义

Status: implemented

## Problem

一次外部审查（在 Linux 上由另一个 agent 复核）在本项目里报出 12 条问题。逐条实证后，9 条为真、2 条不成立、1 条属实现与文档的表述差。真实缺陷集中在两类根因上，而它们都不是"写错一行"，是**同一份知识被抄了两遍**：

**根因一：多处各自持有一份应该唯一的词汇表。**

- `archive-agent-note.ts` 用字面量 `line === "Status: implemented"` 判断状态行，而格式门接受 `状态：已实现`。结果：**一篇能通过门禁的笔记无法被归档**——门禁说它是合法 implemented 笔记，归档器说不认识它。
- `build-board.ts` 自持一份小节名清单，已经漂移成 `曾考虑的替代方案`，而门禁的别名是 `已考虑的替代方案`（"曾"≠"已"），并且少了三个别名。结果：**门禁放行的笔记在看板上渲染为空**。这与 `note-sections.ts` 注释里"唯一真相来源"的说法直接相悖。
- `build-board.ts` 取小节的正式表达式带 `(?=^## |\s*$)`，而 `\s*$` 在 `m` 标志下匹配任意行尾，于是**每个多段落小节都被截断到第一段**——通常正是承载真正理由的那段。

**根因二：封印链的语义没有钉死。**

封印史此前"按到达顺序算链、按 key 排序后写盘"。这两个顺序一旦不同，落盘的文件就不再描述一条合法链，下一次校验会**把项目自己的历史报成被篡改**。触发条件极其平常：**按文件名日期乱序归档**（文件名日期是决策首次提出日，与实际归档日无关）。实测：先归档 `2026-01-01-newer.md`、再归档 `2025-06-01-older.md`，`verify-archived` 立即报 `chain broken` 并退出 1。

其余为真缺陷：归档 CLI 把中文链接文案 `[历史快照：…]` 写进英文笔记（文档只声明看板界面是中文）；`check-note-anchors` 里 `entry.name !== ".agents"` 被紧随其后的 `SKIP_DIR` 里的 `.agents` 完全抵消，是死代码；`{lifecycle}/AGENTS.md` 豁免既未文档化、语义上也说不通（`AGENTS.md` 是仓库级文件）；中英两版 `SKILL.md` 的别名清单都比门禁少一个（漏 `替代方案`）；英文 `note-format.md` 声称状态行"保持英文"，而门禁其实接受中文状态行。

## Decision

**词汇表只允许一份。** 小节名与状态行语法全部由 `scripts/note-sections.ts` 导出，任何需要它们的脚本都必须 import：

- 归档 CLI 用 `statusGrammarFor()` 验证固定头部第三行，不能把正文示例当成状态行；
- `note-parser.mjs` 提供独立解析器，由 `note-sections.ts` 注入共享别名，格式和链接门禁也复用其示例过滤规则；
- `build-board.ts` 在打包时调用同一解析器，并把解析器与词汇表内嵌到浏览器页面；小节以真实二级标题分隔，保留多段正文及代码示例。

**封印链的语义为：落盘顺序即链顺序，按 key 排序。** `seal-store.ts` 先合并、排序、重算链，再由 `sealFileUpdates()` 验证索引、账本和排序并生成完整内容。校验器的 `sealEntries()` 与归档器的 `prepareNewSeal()` 共用这一过程；`commitFileUpdates()` 批量写入，普通 I/O 失败时恢复已改文件。详细边界见[校验与归档一致性](2026-10-10-validation-and-archive-consistency.md)。

**其余按最小改动修正**：跨 Note 链接文案跟随**被归档笔记自身的语言**（标点也随之，英文用半角冒号）；`check-note-anchors` 删掉被覆盖的 `.agents` 例外，改为在注释里说明"笔记不是代码"，并新增 `AGENT_NOTE_CODE_ROOTS`（多个根，按平台分隔符）以便显式指定扫描范围；删除 `ROOT_ALLOWLIST` 死豁免；两版 `SKILL.md` 补齐 `替代方案`；`note-format.md` 两版改为如实说明门禁接受中文状态行、本版只是不使用。

**新增 `scripts/sync-editions.mjs`**（`npm run sync-editions`）：两版共享文件逐字节比对，`--write` 则复制过去，并显式列出"有意不同"的文件，避免把本地化当成遗漏。

## Alternatives considered

- **让归档 CLI 只认英文状态行，并在文档里写明"归档要求英文状态行"**——这是把两个模块的矛盾写进文档当成规格。`状态：已实现` 已经能过门禁，那么"能过门禁的笔记应当能被归档"就是更基本的契约；把限制写进文档只是让用户来承担不一致。
- **保留 `build-board.ts` 自己的词汇表，靠测试断言两份清单相同**——测试只能发现漂移，不能阻止漂移；而这次的真实教训是"两份清单必然会漂移"（它已经漂了，且没人发现）。消除第二份清单比给它加监控更彻底。
- **给封印链加"到达序号"，允许乱序**——会让链的语义依赖一个与内容无关的字段，且无法从文件本身判断顺序是否正确。让链严格跟随排序顺序更简单，也让"落盘即合法"这一性质成立。
- **把归档顺序约束成"必须按 key 升序"并在文档里提示**——把内部不变量变成用户纪律。用户可以、也确实会先归档较新的笔记；正确的做法是让工具不在乎归档顺序。
- **让看板继续截断到第一段，理由是"看板只需摘要"**——那么"截断"就成了功能而非缺陷，需要显式设计（明确取首段并说明）。实际行为是无意的正则副作用，且丢掉的恰是理由部分。

## Consequences

- **收益**：格式门、归档器和两种看板共用别名与解析规则；乱序归档保持有效链；多段小节完整呈现。
- **代价与上限**：解析器和词汇表成为相关入口的共同依赖，安装时必须完整携带。封印写入按路径排序并重算链；修改排序规则属于存储格式决策，不能依靠 `--reseal` 修复损坏的旧链。损坏历史需要可信备份或单独核验，当前没有自动迁移命令。

## Verification

- `npm run test-gates` 覆盖乱序插入、首次写入、中文状态行、多段正文、标题别名、示例过滤、浏览器内嵌解析器与打包结果一致，以及 Git 基线下的合法新增和非法变更。
- `scripts/sync-editions.mjs` 和回归套件逐字节验证两版共享文件；`npm run test-skill-install` 验证实际安装后的运行入口与资源。
- 解析一致性测试在 Node VM 中执行生成页面的真实代码；不代替浏览器交互测试，也未演练损坏历史仓库的人工迁移。
